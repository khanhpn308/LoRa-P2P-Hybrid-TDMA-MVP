# Issue #15 — REST/WSS Contract Invariants (PROPOSED)

**Baseline:** [OpenAPI 3.0.3](openapi.yaml), [WSS](websocket.md) and [WSS JSON Schema](schemas/realtime-event.schema.json). **Status:** `DRAFT/PENDING`; no Go implementation, React integration, Mobile delivery or production security approval. Source BM04/BM05 and system architecture are reference learning/design material, not implementation evidence. The `MUST`s below are proposed until producer/consumer sign-off.

## REST / HTTP semantics

- `GET /healthz` is liveness only (not radio or database readiness). All business paths use `/api/v1`. The new endpoints are **proposed additions** and do not retroactively exist in a deployed service.
- `ADMIN` alone may review/propose activation of a schedule; `OPERATOR` and `VIEWER` must receive 403 even with a valid token. Existing Gateway/Node views require server-side resource-scope checks, not merely `x-roles` field or hidden React buttons. 401 requires `WWW-Authenticate`; 403 means authenticated-but-forbidden; structured `Error` body with `request_id`; logs must redact tokens/secrets.
- `POST /gateways/{gw_id}/schedules/generate` returns 202 only for the queued proposal. `POST /gateways/{gw_id}/schedules/{schedule_id}/review` records APPROVE/REJECT but never activates Gateway. Approved plan stays `PROPOSED` with optional `review_state=APPROVED`; rejected review sets state `REJECTED`. `POST .../activation-requests` (ADMIN only) checks `review_state=APPROVED`, `expected_version`, Owner-approved `activation_window`, three complete announce Superframes (3→2→1), affected Node prepare ACK/old slot lease readiness, Gateway identity and no conflicting staged schedule. Its `202` means dispatch intent persisted, **not** SENT/STAGED/ACTIVE. Backend transitions to SENT only on actual publish; STAGED only on valid `STAGE_ACK`; ACTIVE only on correlated `ACTIVE_REPORT` verified at Gateway. Deadline passed before activation leads EXPIRED; a late report needs reconciliation, not blind state reversal. No cloud per-slot radio control.
- Client POST retries: `X-Idempotency-Key` required for command and activation request (new DRAFT constraint). Scope key to authenticated actor + operation + resource and canonical request fingerprint. Repeat with same fingerprint returns existing 202/ticket; reuse with different payload → 409. Key retention, idempotency store transaction and request canonicalization are implementation decisions pending review; never claim hardware exactly-once. `POST /alerts/{id}/acknowledge` must itself be logically idempotent and never become radio-level ACK.
- `POST /gateways/{gw_id}/nodes/{node_id}/commands` returns `CommandTicket` 202. `GET /gateways/{gw_id}/nodes/{node_id}/commands/{command_id}` provides subsequent state. `NODE_ACKED` proves no physical actuator state unless RF application-level execution proof was designed. Command expiry, retry and observability remain downstream contracts.
- Validate path/query/body; reject unknown keys, trailing JSON garbage, invalid decimals, stale dates, conflicts. Limit body size and rate, but production limits remain TBD. JWT bearer/login is **PROVISIONAL D13**, not approved production scheme. Tokens must not be accepted from URL query.
- Pagination cursor is opaque and scoped to query filters; use deterministic ordering and stable tie-break IDs. All 64-bit identifiers are decimal strings (not JS Number). API version prefix `v1` and schema `1.1.0-draft` are independent of MQTT version. Changes to enum, required fields, operation paths and HTTP error semantics need consumer impact review and version handling; new WSS event types may break exhaustive handlers.

## WSS / state continuity

- AuthN/AuthZ and Origin checked **before** 101 upgrade. No direct MQTT/PG from Web/Mobile and no client-origin mutating WSS events. Subscription v1 derives per-gateway scope from authenticated principal at handshake; same RBAC + object-level checks apply at fan-out. D13 credential transport: `TBD/BLOCKED_SECURITY`.
- Event envelope `event_id` is issued by Backend; `TELEMETRY_UPDATE.payload.event_id` is the stable Gateway-origin business Event ID, assigned once on durable RF acceptance; retained across RF/MQTT retry and Gateway reboot. `node_id` remains authenticated origin metadata. Client must not use WSS envelope ID as telemetry dedup key.
- WSS is best effort; `cursor` does not imply server replay. On connect/reconnect: connect/temporarily buffer live → fetch REST snapshots → apply baseline → drain buffer/reconcile by domain IDs/revision. If overflow, mark STALE and resync. An out-of-order/duplicate `COMMAND_STATE_CHANGED` must not roll back a newer revision. WSS cannot self-certify Gateway online from retained status.
- Future `COMMAND_STATE_CHANGED` is an additive schema proposal with compatibility risks. Unknown event type should be ignored safely and trigger refresh rather than crash. `NODE_ACKED` is protocol-level ACK of the defined type, not verified physical state. Actual WSS origin/auth, pagination, ordering, reconnect and backpressure integration tests: `NOT_VERIFIED`.
